**A task child that hits a usage limit no longer stays `running` until the limit resets, and a limit that names no model family no longer skips the provider's other models.** A usage-limit error now ends the child's turn within one heartbeat interval (10 s by default), even while a terminal monitor or goal timer is live and even when the engine announced a retry that never started, so the parent receives the failure or the child moves to its next fallback rung. A limit the provider confirms as account-wide (an empty balance or credits, a session window, a limit that names the account) skips every other rung on that provider. A limit that names no family, such as "Weekly usage limit reached", tries the next rung on the same provider once, and only when that rung hits a limit too are the provider's remaining rungs skipped. ([#11385](https://github.com/code-yeongyu/oh-my-openagent/pull/11385), fixes [#9711](https://github.com/code-yeongyu/oh-my-openagent/issues/9711) and [#11383](https://github.com/code-yeongyu/oh-my-openagent/issues/11383)) The verdict of that one probe is remembered until the limit resets, so a later task neither probes the same family again nor rediscovers the account limit, and a probe that gives no answer within 60 s counts as the account limit instead of leaving the task waiting.

## 2026-10-26 - Usage-limit turns settle in bounded time; limit scope is confirmed before a provider is skipped (#11388)

`runners/rpc/turn-settlement.ts`: a held usage-limit error (any `usageLimitScope`) settles at its first confirmation,
one `settleConfirmMs` (the handle's heartbeat interval) after its `agent_end`, regardless of live wake sources. An
`agent_end { willRetry: true }` carrying a usage limit is held the same way, so a retry the engine announces but never
starts still settles. After a usage-limit end, a later terminal usage-limit end (a monitor wake, a steer or the engine's
retry re-hitting the spent limit) settles at once. A non-limit error held by a live wake source now re-arms its
confirmation instead of returning without one.

`manager/credential-failure.ts`: `usageLimitScope` returns `account` only when the text proves it (credits, balance,
billing, a session window, the provider naming the account or organization) and `ambiguous` otherwise. senpi's
"<provider> account usage limit has been reached" rewrite does not count as proof. `runtimeFallbackCandidates` drops
every same-provider rung on a confirmed account limit (they used to move last). An ambiguous limit keeps list order, so
the next same-provider rung is tried once. When that rung hits a limit too (the previous attempt ran on the same
provider), the limit is treated as account-wide.

`manager/usage-limit-memory.ts`: the task manager remembers spent limits per provider (account) and per provider + model family until the
stated `Resets at <ISO>`, else `LIMIT_MEMORY_DEFAULT_MS` (60 min). `runtimeFallbackCandidates` skips remembered rungs, and a new task
starts on the first rung the memory clears or is refused at spawn with the remembered reason. Any failure of the probe rung confirms the
provider's account limit. `manager/usage-limit-probe.ts`: the probe rung's outcome is bounded by `limitProbeTimeoutMs`
(`LIMIT_PROBE_TIMEOUT_MS`, 60 s) until it starts answering.
