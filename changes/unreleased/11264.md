**Memory sync and the `memory` tool no longer hang while a macOS keychain approval dialog is open.** A session's sign-in read now gives up after 5 s with an error that names the "bun wants to access key omo-cli" dialog to answer, instead of waiting with no end. Memory sync skips that pass, logs why, and tries again every 15 s, and the `memory` tool returns at once. All reads in one process share the one keychain request that is still waiting, so parallel sessions no longer stack a blocked read (and another dialog) per request, and when the dialog is approved late, the next read uses that answer. `omo login`, `omo whoami`, `omo account` and `omo sync` still wait for the dialog, and now say so after 2 s. ## 2026-10-25 - memory sync defers a pass while the keychain waits for approval (#11264)

`device-session/account-source.ts` turns the credential store's `KeychainApprovalPendingError` (a session read past its 5 s deadline in `service-auth/keystore.ts`) into `SyncSessionDeferredError` (`sync-session-deferred.ts`, matched by its code because the account sidecar carries its own copy of the class), and `signedOut()` answers false while the keychain waits, so a pending keychain never reads as signed out. `sync-runner.ts` logs the store's message, leaves the repo idle (status `null`, so the `memory` tool's status read returns at once), and launches the pass again after `deferredRetryMs` (15 s) while the same sessions still hold the repo.

Must not break: a retry joins the process's one parked keychain read instead of starting another, so it adds no prompt; a pass that resolves the session normally schedules no retry.
