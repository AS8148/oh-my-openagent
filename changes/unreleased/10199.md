**A memory writer killed mid-commit no longer leaves the next writer stuck on a git lock, and a live commit's lock is never taken.** When a memory writer dies holding a git `index.lock` or ref lock, the writer that takes over its memory-write lock now removes that lock, but only after proving the previous owner dead, seeing no other process still working in the repository (a killed writer's own git command can outlive it), and seeing no process holding the file open. When any of that cannot be proven, including when the open-file check is slow or never answers, the lock stays put and the write fails with an error that names each lock file, says why it was kept, and gives the way out: `/memory unlock <path>` re-checks that one lock, shows what it found, refuses while any live holder, repository user or memory writer is visible, and removes only that file after you confirm (`--force` skips the prompt in a non-interactive session, never a refusal). On Linux desktops and SSH logins where some of your own processes cannot be inspected, the automatic removal does not fire and this command is the way out; [#10322](https://github.com/code-yeongyu/oh-my-openagent/issues/10322) tracks making liveness independent of `/proc`. On Linux this check reads `/proc` directly, so recovery also works on minimal installs and containers without `lsof`.
